## Context / Problem

**As-is.** Правила цены для ЯМ разрознены (калькуляторы, ручные правки, наследие плагина `ym` / YMWB). Нет единого контура, где коммерция задаёт тарифы/формулы, система считает ЯЦ по SKU и **кладёт готовый результат в БД** для последующей передачи на Маркет.

**To-be.** RULI считает цену оффера для ЯМ (ЯЦ / P) по согласованным правилам (макет выше) и **сохраняет** в БД подготовленный пакет полей для передачи (`offerId`, `value`, опц. `discountBase`, метаданные расчёта, признак «готово к отправке»). Фактический POST в Partner API — вне этой фичи.

Контекст канала Маркета (для соседней фичи, не AC этого PRD): на кабинете `861370` цена принимается только business-URL; campaign даёт `LOCKED` при `onlyDefaultPrice`.

## Scope

### In

- UI/логика ценообразования по канону макета `ym-price-mgmt-ui-example.html` (справочники + расчёт).
- Расчёт ЯЦ (P) по формулам и справочникам: К, ПМ/СПМ, СМ, П, Э, M, скидки, наценки, буст, floor, округление.
- Входы расчёта: розничная/закупочная цена, вид/бренд/сет, объём (л), категория Маркета (для К% — чтение справочника FEE допустимо).
- **Сохранение в БД** результата по SKU/`offerId`: цена к передаче, опц. `discountBase`, снимок ключевых входов/тарифов, статус готовности, время расчёта.
- Отбор кандидатов: список к подготовке / исключения из продажи на ЯМ (правила отбора данных; сам push — не здесь).
- Тест расчёта одного SKU в UI (секция 6 макета) с записью/предпросмотром того, что уйдёт в БД.

### Out

- **Отправка цен в Яндекс Маркет** (Partner API `offer-prices/updates`, CLI/cron `shop ym`, карантин Маркета, логи HTTP к Маркету) — **отдельная фича**.
- Карточка / маппинг (`F-CATALOG`), остатки (`F-STOCK-SYNC`), заказы (`F-ORDERS`).
- Суточный зонд FEE% / страница «Комиссии по категориям» как отдельный пакет (`origin/fee-categories`) — **чтение** `fee_pct` в расчёт ок, sync FEE — не этот PRD.
- YMWB; взаиморасчёты Маркета.

## Outcome (Definition of Done фичи)

Для SKU из контура ЯМ в БД есть актуальная запись «цена к передаче»: идентификатор оффера, значение ЯЦ (и при необходимости `discountBase`), признак готовности и достаточно метаданных, чтобы **отдельная фича отправки** могла сформировать тело Partner API без пересчёта формул.
- Смена URL CLI на `businesses/{business_id}/offer-prices/updates`
- В теле `"offerId"` (допустимо дублировать `"id"`)
- Узкий `set_products`; интервал `cli_upload_prices` > 0
- `discountBase` только если проходит правило 5–75%

### Out

- Цена на один склад / один `warehouseId` (API не умеет)
- Уникальные цены по `campaignId`, пока `onlyDefaultPrice` = true
- Карточка (`F-CATALOG`), остаток (`F-STOCK-SYNC`)
- Кнопка UI «в Яндекс.Маркет» для цены (пока нет — не обязательна в P0)
- YMWB

## Business rules (локальные для фичи)

| ID | Правило | Источник |
|----|---------|----------|
| BR-1 | ЯЦ (P) считается так, чтобы при целевой M покрывались удержания (К, ПМ с капом СПМ, СМ по объёму, П, Э) ± скидки/наценки/буст; при P выше порога ПМ% → ветка с фикс. СПМ | макет `ym-price-mgmt-ui-example.html` |
| BR-2 | Локальная средняя миля: СМ = 0 ₽; иначе СМ по таблице объёма, не выше капа СМ | тот же макет |
| BR-3 | Итоговая P: max(расчёт, floor); округление вверх к шагу, если шаг > 0 | макет |
| BR-4 | `discountBase` в БД только если на 5–75% выше `value`, иначе поле пустое/не пишется | плагин `ym` (`getDataForAddPricesByHash`) — правило полезно соседней выгрузке |
| BR-5 | SKU в исключениях или вне списка подготовки — запись «к передаче» не создаётся / снимается с ready | макеты exclusions / export (логика отбора) |
| BR-6 | Успех фичи = запись в БД, не факт появления цены в кабинете Маркета | граница scope |

| BR-2 | Нет поля склада в теле цены | дока updateBusinessPrices + ответ 2026-09-02 |

## Flows

### Happy path

1. Коммерция задаёт тарифы и правила (UI по макету).
2. Для SKU-кандидата считается ЯЦ (P); при необходимости — `discountBase`.
3. Система **сохраняет в БД** пакет: `offerId`, `value` (= ЯЦ), опц. `discountBase`, статус `ready` (или эквивалент), timestamp, снимок входов.
4. Соседняя фича отправки (вне scope) читает ready-записи и шлёт в Маркет.
1. Цена SKU в Shop.
2. `php cli.php shop ym 17` при включённой загрузке цен и узком сете.
3. POST `…/businesses/861370/offer-prices/updates`.
4. Кабинет: цена на всех магазинах (лаг / карантин).

### Fail / edge

| Кейс | Ожидание |
|------|----------|
| Знаменатель формулы ≤ 0 | P не считается; в БД нет ready-успеха; ошибка расчёта |
| Нет обязательных входов SKU | ошибка; ready не ставить |
| `discountBase` вне 5–75% | в БД только `value` |
| SKU в исключениях / вне списка | не в выборке ready к передаче |
| Оператор смотрит кабинет Маркета | изменение цены там **не** AC этой фичи |

### Расчёт ЯЦ (канон макета — уточнить)

```text
ЯЦ = (РЦ - СКИДКА + НАЦЕНКА + СМ + П) / (1 - K - Э - ПМ)
```

Если расчётная цена выше порога, где ПМ% упирается в кап СПМ:

```text
ЯЦ = (РЦ - СКИДКА + НАЦЕНКА + СПМ + СМ + П) / (1 - K - Э)
```

В JS макета P_min также от закупки C и целевой M; финальный канон «РЦ vs C+M» — open question.
Код: `apiGetOfferPricesUpdates`, `getApiUrl('/offer-prices/updates')` (сейчас `campaigns=true`).

## Acceptance criteria

### Удачные сценарии

**Расчёт ЯЦ.** В системе уже лежат тарифы и правила: K, ПМ, СПМ, таблица СМ, П, Э, M, скидки, наценки. У SKU на месте входы для формулы — закупка или розница, вид, бренд, сет, объём. Считаем ЯЦ. На выходе — нормальное число P (не «пусто» и не бесконечность). Если задан минимум цены (floor > 0), P не ниже него. Если задан шаг округления (> 0), P поднимаем вверх до этого шага. Для локальной средней мили в расчёт идёт СМ = 0 ₽, а не ступень из таблицы объёма.

```gherkin
Given в справочниках заданы K, ПМ, СПМ, таблица СМ, П, Э, M, скидки и наценки
And у SKU есть закупка или розница, вид, бренд, сет и объём
When считаем ЯЦ
Then получается конечное P
And если floor > 0, то P не ниже floor
And если шаг округления > 0, то P округлена вверх к этому шагу
And при локальной средней миле СМ в формуле равна 0
```

**Сохранение в БД.** SKU в списке на подготовку, не в исключениях, ЯЦ уже посчитана. После сохранения в базе есть строка с этим `offerId`: цена = ЯЦ после округления, валюта RUR, флаг «готово к передаче» (или тот же смысл другим полем), время расчёта заполнено.

```gherkin
Given SKU в списке подготовки и не в исключениях
And ЯЦ уже посчитана
When сохраняем результат
Then в БД есть запись с offerId этого SKU
And price_value совпадает с ЯЦ после округления
And currency = RUR
And стоит признак ready_to_push (или эквивалент)
And calculated_at не пустой
```

**Зачёркнутая цена.** `value` и `discountBase` укладываются в коридор «на 5–75% выше value». В базу пишем оба поля.

```gherkin
Given value и discountBase в коридоре 5–75%
When сохраняем результат
Then в БД есть и price_value, и discount_base
```

### Отказы и края

**Ломаный знаменатель.** Доли в формуле съедают 100% и больше (знаменатель ≤ 0). ЯЦ не считаем успехом: ready не ставим, пишем ошибку расчёта.

```gherkin
Given знаменатель формулы ЯЦ ≤ 0
When считаем ЯЦ
Then ready_to_push для SKU не становится успешным
And в логе или статусе видна ошибка расчёта
```

**discountBase вне коридора.** Зачёркнутая цена не проходит правило 5–75%. В базе остаётся только обычная цена, `discount_base` пустой.

```gherkin
Given discountBase вне коридора 5–75% к value
When сохраняем результат
Then price_value в БД есть
And discount_base пустой или null
```

**Не тот ассортимент.** SKU в исключениях или вообще не в списке подготовки. В пакете «к передаче» у него нет ready.

```gherkin
Given SKU в исключениях или вне списка подготовки
When собираем пакет к передаче
Then у этого SKU нет ready_to_push = true
```

**Граница фичи.** Расчёт и запись в БД прошли. В кабинете Маркета цену для приёмки этой фичи смотреть не нужно: в Partner API из этого scope никто не ходил.

```gherkin
Given расчёт и сохранение в БД уже успешны
When смотрят кабинет Яндекс Маркета
Then для закрытия этой фичи цена в кабинете не обязана измениться
And вызова Partner API в рамках этого scope не было
| WA `plugins/ym` | URL + ключ `offerId` в CLI цен |
| Partner API | `updateBusinessPrices` |
| Кабинет 861370 | цена всех магазинов |
