## 1. Зачем

Оператор должен держать на Яндекс Маркете витрину того же класса, что Ozon: товары из согласованного списка Shop уходят карточкой, затем ценой и остатком, без ручного Postman и без выгрузки «всего каталога наугад».

Сейчас Partner API на одном SKU доказан. Плагин `ym` не даёт процесса: нет списка-аналога `ozon-24`, нет отсева дырявых карточек, нет hash, нет реестра «уже на МП», нет справочника складов, цены CLI бьют в LOCKED campaign, один `warehouse_id` на профиль.

Без отдельного контура «все товары» либо не поедут, либо обнулят чужие склады / зальют мусор.

## 2. Инварианты (не обсуждаются в разработке)

| # | Правило |
|---|---------|
| I-1 | **Код Ozon не трогать.** Ни `wa-apps/ozon`, ни таблицы `ozon_*`, ни CLI, ни общие «хелперы из ozon», ни копипаст классов с заменой имени. |
| I-2 | Контур ЯМ **проектируется и пишется с нуля**: свои сущности, свои job’ы, свой клиент Partner API, свои логи. |
| I-3 | Источник карточки — **тот же Shop**, что у Ozon (`shop_product` + SKU + features + фото). PIM карточки МП не шлёт. |
| I-4 | Ключ оффера ЯМ = **`shop_product_skus.id`** (как в заказах `1107932`, `726138` и у Ozon `offer_id`). Не колонка YMWB `Sklad`. |
| I-5 | Цена ЯМ — **на кабинет** (`businessId`), не на склад. Остаток — **на пару** `(campaignId, warehouseId)`. |
| I-6 | На бою **запрещён** hash `all`. Только явный список Shop. |
| I-7 | YMWB вне скоупа. Заказы / возвраты — не этот контур (`F-ORDERS`). |

Ozon используется **только как описание процесса** (список → гейты → hash → реестр → отдельные job’ы → склады). Поведение API и данные — свои.

## 3. Границы

### In

- Отбор SKU для ЯМ (список Shop + гейты качества).
- Сборка и отправка карточки (mappings; позже — категорийные характеристики).
- Отправка цены кабинета.
- Отправка остатка по настроенным складам ЯМ.
- Реестр выгрузки, hash, дельта остатка, журналы, ручной «дослать один sku».
- Справочник: склад ЯМ ↔ склады Shop ↔ список(и) ↔ campaign.

### Out

- Любые изменения в приложении/таблицах Ozon и WB.
- Генерация карточки в PIM / 1С.
- Уникальная цена на каждый `warehouseId` (API кабинета `onlyDefaultPrice` это запрещает).
- Одновременный прогон всех 18 складов 861370 в первом релизе.
- Карусель «весь активный каталог без списка» (у Ozon запасной CLI; здесь — не MVP).
- UI «галка в каталоге → в Маркет» как основной канал (у текущего `ym` он ещё и врёт успех).
- Приёмка заказов, ярлыки, first-mile.

## 4. Стейкхолдеры и роли

| Роль | Делает | Не делает |
|------|--------|-----------|
| Контент | Ведёт список ЯМ; маппинг `part_type` → категория ЯМ (когда появится); чинит дыры гейтов | Не шлёт Postman на каталог |
| Операции / склад | Какие склады ЯМ живые; какие `stock_id` Shop на какой warehouse | Не подтверждает чужие остатки «чтобы проверить» |
| Коммерция | Правило витринной цены и `discountBase` (Q-003) | Не ждёт цену «только МСК» |
| ИТ | Job’ы, мониторинг, запрет `all` | Не чинит Ozon «заодно» |
| Кабинет Маркета | SoT витрины после API | Не место массового заведения карточек |

## 5. To-be процесс (бизнес)

Три независимых потока. Общий вход — **список ЯМ**. Цены и остатки имеют право идти **только** по SKU из **реестра** (карточка уже принята кабинетом или хотя бы успешно ушла mappings).

```text
[Список Shop «ЯМ»]
        │
        ├─► Job КАРТОЧКА
        │     гейты → hash не менялся? skip
        │     иначе POST offer-mappings/update
        │     успех → строка реестра + (опц.) постановка в очередь цены/остатка
        │
        ├─► Job ЦЕНА          (по реестру)
        │     POST businesses/{id}/offer-prices/updates
        │
        └─► Job ОСТАТОК       (по реестру × склады из справочника)
              PUT campaigns/{campaignId}/offers/stocks
              дельта; 0 только если товар пропал с витрины этого склада
```

Ручной контур: «выгрузить sku_id X» — те же гейты и те же URL, без обхода списка.

### 5.1 Карточка

1. Берём SKU из списка ЯМ (карусель по `product_id` / `sku_id`, с чекпоинтом last_id).
2. Гейты (как смысл Ozon, свои проверки): товар включён; есть фото; вес; габариты; `part_type`; бренд/производитель. Нет категории ЯМ на этапе 2 — карточка **базовая** (имя, vendor, barcode, описание, ТН ВЭД, фото, вес/габариты) как эталон Postman `1107932`. Нет категории на этапе 3 — SKU в «карантин списка», в API не идёт.
3. Считаем hash канонического payload. Совпал с сохранённым — skip (экономия лимита content).
4. Чанк (ориентир: десятки, не тысячи) → Partner API.
5. Успех: реестр + hash. Ошибка API: лог, SKU остаётся кандидатом, не помечается «выгружен».

### 5.2 Цена

1. Только реестр (карточка есть).
2. Цена из Shop (тот же источник, что витрина; не `base_price` склада как отдельный канал — уточнить Q-цены).
3. `discountBase` только если проходит правило Маркета 5–75% к `value`; иначе уходит одна `value`.
4. Одна цена на весь кабинет 861370: смена в Shop меняет **все** магазины кабинета. Это ожидаемо, не баг.

### 5.3 Остаток

1. Для каждой **включённой** строки справочника складов: склады Shop → сумма count → `warehouseId` + `campaignId`.
2. Сравнение с последним успешно отправленным count.
3. PUT только new/change/delete; `updatedAt` = сейчас в часовом поясе Маркета.
4. Ниже порога «не продаём» (аналог `min_stock` / `min_price`) — count **0** по этой паре, не молчание.
5. MVP: одна пара **1669219 / 137514772**. Остальные 17 — отдельные включения в справочнике, не «включить все».

### 5.4 После новой карточки

Бизнес-ожидание: новый SKU на витрине не ждёт «до завтрашнего cron цены». После успеха mappings тот же sku ставится в короткую очередь цены и остатка (аналог смысла Kafka `mp:wb`, **своя** очередь ЯМ, не топик Ozon).

## 6. Сущности (логические, не схема Ozon)

Имена таблиц — рабочие; физическая схема — в реализации. **Префикс свой (`ym_…`), не `ozon_…`.**

| Сущность | Зачем |
|----------|--------|
| Список Shop | Кого выгружаем. Отдельный `shop_set` (Q-009). Не переиспользовать `ozon-24`. |
| Карантин / ошибки гейта | Куда падают SKU без фото/веса/`part_type`. Можно второй сет. |
| Реестр оффера | `sku_id`, `offerId`, статус карточки, last hash, last error, timestamps |
| Справочник склада ЯМ | `warehouseId`, `campaignId`, имя, on/off, какие `stock_id` Shop, какие списки |
| Последний остаток | `(sku_id, warehouseId)` → count, `updatedAt` отправки |
| Чекпоинт job | last_id / last_time, чтобы карусель не начиналась с нуля каждый запуск |
| Маппинг категории | `part_type` → `marketCategoryId` (+ parameterId). Этап 3, не блокер MVP карточки-эталона |

Клиент HTTP и креды — **профиль ЯМ / кабинета**, не OAuth Ozon.

## 7. Бизнес-правила

| ID | Правило |
|----|---------|
| BR-1 | Нет в списке ЯМ → карточка/цена/остаток этим контуром не уходят. |
| BR-2 | Нет в реестре → цена и остаток не уходят (кроме явного админ-режима «форс», не для cron). |
| BR-3 | Гейт не пройден → API не вызывается; причина видна контенту. |
| BR-4 | Hash совпал → карточка не вызывается. |
| BR-5 | Цена только `POST /v2/businesses/{businessId}/offer-prices/updates`. Campaign-URL = инцидент (LOCKED). |
| BR-6 | Остаток только `PUT /v2/campaigns/{campaignId}/offers/stocks`, массив `skus`, один `warehouseId` в элементе. |
| BR-7 | Старый `updatedAt` считается **провалом**, если count в кабинете не сменился (даже при HTTP 200). |
| BR-8 | Cron не имеет режима «весь каталог Shop». |
| BR-9 | Выключение склада в справочнике = этот контур перестаёт слать на него; не массовый 0 «на всякий случай» без отдельного решения операций. |
| BR-10 | Инцидент Ozon / правка Ozon **не** входит в задачи этого контура. |

## 8. Где жить коду (решение ещё открыто)

Код Ozon не используем в любом варианте. Развилка только **куда класть новый контур ЯМ**:

| Вариант | Суть | Плюс | Минус |
|---------|------|------|--------|
| **N1** Новый модуль/приложение WA только для витрины ЯМ | Как `wa-apps/ozon` по роли, своя кодовая база | Чистая граница; `plugins/ym` остаётся заказам | Второй «остров» в WA |
| **N2** Новый пакет **внутри** `plugins/ym`, но новые классы/CLI, без развития текущего `shopYmCli` | Один плагин на канал ЯМ | Меньше приложений | Риск смешать со старым CLI |
| **N3** Патчить текущий `shopYmCli` «добавить hash» | Быстрее на бумаге | — | Не «с нуля»; тянет LOCKED/`all`/один склад |

Рекомендация аналитики: **N1 или N2**. Не N3 как целевой процесс. Текущий `shop ym {profile}` на бою с `all` **не включать**. Слой A (починка URL цены/тела) либо входит в новый клиент N1/N2, либо остаётся точечным патчем старого CLI только для отладки одного SKU — не для каталога.

`D-YM-CARD-GEN` (proposed) совпадает с N1/N2 по месту, но **устарел** в части `offerId = Sklad`. Для этого БА канон — `sku_id`. D нужно переутвердить отдельно, не блокируя MVP базовой карточки (эталон Postman без дерева категорий).

## 9. Волны поставки (бизнес, не спринт)

| Волна | Что умеем сказать бизнесу | Зависимость |
|-------|---------------------------|-------------|
| **B0** | Список ЯМ заведён; `all` технически невозможен; гейты пишут карантин | Операции: какой set_id (Q-009) |
| **B1** | Cron карточки по списку: эталонные поля, hash, реестр; кабинет обновляется без Postman | Клиент business mappings |
| **B2** | Cron цены по реестру, URL кабинета, без LOCKED | B1; правило `discountBase` |
| **B3** | Cron остатка на **1669219** / 137514772; дельта; свежий `updatedAt` | B1; маппинг `stock_id` Shop → этот склад |
| **B4** | После новой карточки цена и остаток уходят в том же окне, не «на следующем суточном cron» | B2+B3 |
| **B5** | Включение следующих складов по одной строке справочника | Q-007; операции |
| **B6** | Категории/параметры ЯМ (`offer-cards`) | Принятый D-YM-CARD-GEN + контент |

Пока нет B0+B1, фраза «выгрузить все товары» со стороны разработки отклоняется.

Слой A из чеклиста Postman **обязателен как поведение API** в B1–B3 (не как правка Ozon).

## 10. Критерии приёмки (бизнес)

На узком списке (не меньше эталона `1107932` + несколько SKU из карантина):

1. SKU без фото в API **не** ушёл, виден в карантине.
2. Смена названия в Shop → после job карточки кабинет совпадает (лаг минут допустим). Повтор job без изменений → **нет** лишнего POST (hash).
3. Смена цены Shop → все магазины кабинета, не «только тестовая campaign».
4. Смена остатка на складе Shop, сматченном на 1669219 → count там; другие склады кабинета **не** обнулились.
5. Job с пустым/запрещённым «весь каталог» не стартует.
6. Репозиторий Ozon в diff задачи **пустой**.

Негатив: campaign-URL цены в логе = fail волны B2.

## 13. Следующий артефакт

1. Операции закрывают Q-009 и склад 1669219 → Shop `stock_id`.
2. ИТ выбирает N1 или N2 (короткий decision, не этот файл).
3. Переутверждение `D-YM-CARD-GEN`: `offerId = sku_id`; категории = волна B6; код с нуля, Ozon freeze.
4. Feature PRD на волны **B0–B3** (не на весь B6) — после выбора N1/N2. Текущие `F-CATALOG` / `F-PRICE` / `F-STOCK` остаются контрактом **API**, не контрактом «форк Ozon».
