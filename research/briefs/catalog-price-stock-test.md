## Порядок

Идём строго сверху вниз. После каждого блока — таблица «было / стало» и кусок лога. Дальше не идём, пока блок не закрыт.

### 0. Подготовка лога

1. Запомнить размер/хвост текущего `query.17.log` (или скопировать файл в сторону).
2. Дальше смотрим **только новые** строки с `offer-mappings`, `offer-prices`, `offers/stocks`.

**Правильный вход — заказ, который уже приняли:**

1. Магазин → Заказы → **`2534310`** (параметр `ym_order_id` = `61089913793`).
2. В составе заказа открыть позицию. Записать `product_id` и `sku_id` из строки заказа.
3. Если `sku_id` / `product_id` = **2** (или артикул `deleted`) — товара в каталоге **нет**. Плагин подставил заглушку. Тогда SKU `1107932` для теста карточек/цен/остатков **не годится**: нужен другой оффер, который есть и в кабинете, и в Shop.
4. Если sku живой — открыть этот товар из строки заказа (не поиск `1107932`).
5. Дополнительно поиск: **`JB-22282`**, «прокладка MAZDA», код артикула (не id).

### 4. Карточка — один товар (UI)

Цены и остатки этим шагом **не** уходят.

Пункты **не на** `#/product/…/edit/`. Блок только в **списке**.

**Баг:** если поставить галку на строке, JS шлёт в API `product_id`, **без** hash коллекции. `getDataForAddOfferByHash` получает не `id/1042543` → 0 офферов → 100% и «Отправлено без ошибок» **без** вызова Маркета и **без** строк в `query.17.log`.

Обход (один товар, валидный hash):

1. Список: `https://test.ruli.ru/webasyst/shop/?action=products#/id/1042543/`
2. Галка **«выбрать все»** на этом списке (в коллекции один товар) — не галка только в строке на общем каталоге.
3. Левая колонка → **«Отправить товар»** → **«в Яндекс.Маркет»**.
4. В диалоге явно профиль **17** (первый FBS в списке может быть другим → лог уйдёт в `query.{другой id}.log`).
5. Отправить. В `query.17.log` должен быть `offer-mappings/update.json`.

Или: поиск, после которого в списке **только** этот товар, затем «выбрать все».

6. **Стоп.** Лог + кабинет.

### 5. Цена — один SKU (узкий список + CLI)

UI плагина цену не шлёт.

1. Магазин → **Списки**: создать временный список, например `ym-test-1107932`, **один** товар.
2. Профиль 17: «Список товаров для работы…» = этот список. Сохранить.
3. Записать цену Shop и цену кабинета **до**.
4. В Shop сменить цену SKU на тестовую (запомнить старую).
5. В профиле 17: интервал загрузки **цен** не «Не загружать»; галка **сбросить** последний запуск цен.
6. Карточки и остатки на этот запуск **оставить «Не загружать»**, чтобы не уехать всё сразу.
7. На сервере (не с рабочей станции без доступа):

   `php …/cli.php shop ym 17`

8. Хвост лога: `…/offer-prices/updates.json`, `"id": "1107932"` (или shopSku), `value` = тестовая цена.  
   Postman 2026-09-02: campaign-URL → `LOCKED` / `Partner use only default price`. На 861370 цена только через `POST …/businesses/861370/offer-prices/updates`. CLI плагина ходит в campaign — тот же LOCKED вероятен.
9. Кабинет: цена (лаг/карантин возможен).
10. **Вернуть цену Shop** на исходную. Повторить CLI **или** оставить возврат на шаг 7 — но исходную цену в Shop вернуть сразу.

11. **Стоп.**

### 6. Остаток — один SKU (тот же список + CLI)

1. Тот же временный список и профиль 17.
2. Записать остаток Shop и кабинет **до**.
3. Сменить остаток **этого** SKU на тестовый (не обнулять чужие склады).
4. Интервал загрузки **остатков** не «Не загружать»; сбросить последний запуск остатков. Цены и карточки — «Не загружать».
5. Снова `php …/cli.php shop ym 17`.
6. Лог: `…/offers/stocks.json`, `sku` = 1107932, `warehouseId` из профиля, `type: FIT`, `count`.  
   Postman 2026-09-02: `warehouseGroups: []` → `POST …/v3/businesses/861370/offers/stocks/update`, `partnerWarehouseId` **1669219** (campaign 137514772, «Ruli МСК 1 день»). Не слать `count: 0`, если не скрываешь оффер. Чужие склады кабинета не трогать.
7. Кабинет: остаток.
8. **Вернуть остаток Shop.**

9. **Стоп.**

### 7. Откат настроек

1. Профиль 17: вернуть исходный «Список товаров…» (не оставить тестовый сет на cron).
2. Интервалы CLI — как было до теста.
3. Временный список `ym-test-1107932` можно оставить для следующего прогона или удалить.
