# Логика организации репозитория

**Это живой документ.** Меняете правила папок — сначала правьте этот файл, потом структуру и `AGENTS.md` / `WORKSPACE-INDEX.md`.

Версия логики: `0.1`  
Дата: `2026-08-24`  
Проект: Яндекс Маркет ↔ RULI

---

## 1. Назначение репозитория

| Да | Нет |
|----|-----|
| Смысловая модель проекта (AS IS, граф, Feature PRD) | Монорепо кода WA/1С/PIM/MPS |
| Playbook оркестрации агентов | Статусы спринта как SoT (SoT — Трекер) |
| Якоря на код/БД/Трекер | Секреты и PII в git |
| Артефакты для комитета / разработки | Полный дамп задач Трекера |

Один repo = **аналитическая память проекта**, не «весь Честный знак / весь ЯМ в git».

---

## 2. Три рабочих слоя (инвариант)

Порядок обязателен для агентов и людей:

```text
research/  →  decisions/  →  graph/  →  features/
   AS IS        Options       влияние      контракт
```

| Слой | Папка | Вопрос, на который отвечает |
|------|--------|------------------------------|
| 1. Исследования | `research/` | Как есть? Где evidence? |
| 2a. Решения | `decisions/` | Какой вариант и почему? |
| 2b. Граф | `graph/` | Что от чего зависит при изменении? |
| 3. Поставка смысла | `features/` | Что именно делать разработке и как принять? |

**Правило:** Feature PRD не пишется «с хотелки», пока нет Reality Brief (или явного исключения для T1 Fast Lane — см. `orchestration/lanes.md`).

**Правило:** фича с `depends_on` на открытый `D-*` не уходит в глубокий PRD.

## 3. Назначение каждой папки

### `meta/`

Мета-правила репозитория. Сюда — логика структуры, соглашения об ID, changelog структуры.

- Меняется редко, но осознанно.
- Агенты читают перед реорганизацией.

### `context/`

Project Context Pack — «карта мира», редко переписывается целиком.

| Файл | Содержание |
|------|------------|
| `00-charter.md` | outcome, границы, стейкхолдеры |
| `01-systems.md` | системы, SoT, интеграции |
| `02-constraints.md` | нельзя ломать, сегменты, NFR |
| `03-tracker.md` | ссылки на INI / проект Tracker |

Не класть сюда детальные BR фич — только то, без чего нельзя понять проект за час.

### `research/`

Исследования для формулировки AS IS.

| Подпапка | Содержание |
|----------|------------|
| `as-is/` | синтезированные описания процесса/систем/данных |
| `evidence/` | сырьё: code / db / tracker / external |
| `briefs/` | Reality Brief, Open Questions |

**Evidence packs** — не мнения: code anchor, schema anchor, data sample, counterexample, invariant.

Сырые выгрузки с PII — локально; в git только обезличенные выжимки (см. `.gitignore`).

### `decisions/`

Один файл = одно решение (`D-XXXX-slug.md`).  
Шаблон: `_template.md`.

Пока decision открыт — зависимые фичи в графе помечаются, PRD не углубляется.

### `graph/`

| Файл | Роль |
|------|------|
| `graph.yaml` | **канон** (источник правды) |
| `graph.md` | вид для человека (mermaid, навигация) |
| `schema.md` | типы узлов и рёбер |
| `views/` | подграфы по волнам (опционально) |

Слой 1 графа держать обозримым (~15 фич / ~10 разделяемых правил на картинке).  
Детали фичи — в `features/F-*/`, не раздувать YAML задачами Трекера.

### `features/`

| Элемент | Роль |
|---------|------|
| `F-XXXX-slug/PRD.md` | контракт фичи |
| `_template/` | шаблон |
| `STATUS.md` | таблица id → статус → волна → Tracker |

Итерации: сначала ключевые (foundation → inbound/outbound core → exceptions).  
При изменении `R-*` — blast radius из графа → патч соседних PRD.

### `orchestration/`

Playbook агентов: router, lanes, handoff-схемы.  
Это **как работать**, не **что решили по ЯМ**.

### `refs/`

Стабильные указатели: пути к кодбазам, какие MCP/БД, query Трекера.  
Без клонов репозиториев внутрь YM_Ruli.

### `secrets/`

Только локально. В git — `README.md` с инструкцией.  
Значения переменных — `local.env` или Cursor secrets / `~/.cursor/secrets/`.

### `.cursor/rules/`

Правила Cursor для этого workspace: слои, Tracker read-only, запрет коммита секретов.

## 4. Соглашения об идентификаторах

| Префикс | Где | Пример |
|---------|-----|--------|
| `F-` | feature в graph + папка features | `F-PRICE-SYNC` |
| `R-` | разделяемое бизнес-правило (граф) | `R-STOCK-SOURCE` |
| `D-` | decision | `D-PUSH-VS-POLL` |
| `E-` | сущность | `E-OFFER` |
| `C-` | capability / платформенный кусок | `C-MPS-YM` |
| `W-` | волна / milestone | `W1-FOUNDATION` |

Правило слой 1: узел `R-*` только если правило делят **≥2** фичи. Иначе — внутри Feature PRD.

Задачи Трекера (`INI-*`, `DEVEL-*`, …) — ссылки/`refines`, не отдельные узлы графа по умолчанию.

## 5. Что агентам читать в каком порядке

1. `AGENTS.md` (этот контракт поведения)
2. `meta/FOLDER-LOGIC.md` (если сомнение куда класть)
3. `context/00-charter.md` + `features/STATUS.md`
4. Нужный слой: `research/` | `graph/` | `features/F-…`

Писать — только в целевой слой; не размазывать один факт по трём папкам без ссылок.

---

## 6. Как корректировать эту логику

1. Описать изменение в разделе **«Changelog логики»** ниже.
2. Обновить затронутые абзацы этого файла.
3. Привести в соответствие дерево папок (если нужно).
4. Синхронизировать `AGENTS.md` и `WORKSPACE-INDEX.md`.
5. При смене инварианта слоёв — обновить `.cursor/rules/project.mdc`.

Не удалять changelog: нужна история «почему папки так».
